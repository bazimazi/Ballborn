Ballborn source review and comparable-game research

Reviewed on 2026-09-28, against commit `e782565` and the clean working tree present at the start of the review. The companion [AI improvement prompt](ai-improvement-prompt.md) translates these findings into an implementation brief.

**Assessment.** Ballborn has a distinctive foundation worth preserving: equipping parts changes the physical character of the player, and positioning supplies the attack. Its immediate priority is making those rules dependable and legible. More content will have greater value after progression, damage, room completion, and input behave consistently.

**Scope and evidence.** I inspected the TypeScript modules, content definitions, HTML, CSS, package scripts, and configuration. I ran the production build, the existing physics self-check, and isolated Node probes against bundled source using the installed esbuild dependency. Some probes invoke TypeScript-private methods after transpilation to isolate a behavior; they are diagnostic evidence, not end-to-end browser tests. I did not conduct a human playtest, visual browser review, audio audition, controller hardware test, or performance benchmark. Findings below distinguish reproduced behavior, source-level findings, and design recommendations. No game implementation or dependencies were changed.

**Existing strengths and inventory.**

- TypeScript with strict checks, Vite, Canvas 2D, DOM menus, and synthesized Web Audio. No runtime game engine.
- Six equipment slots: core, shell, momentum, impact, ability, passive. Additive and multiplicative modifiers compile into clamped stats.
- 35 components: 29 standard parts, three evolutions, and three fusion results. There are 11 tag-based synergies, 12 regular enemy definitions, 14 achievements, and three fusion recipes.
- 27 room templates, including the two introductory rooms, one biome, and the separate three-phase Iron Colossus implementation. Shop, event, and treasure nodes use menus rather than physical room templates.
- A six-layer route pattern, randomized links and room selection, per-run currency, permanent unlocks, and Heat 0–3.
- Coyote time, jump buffering, mass-dependent movement, collision impulses, projectile reflection, status effects, readable component tradeoff copy, reward animations, and a no-stakes Ball Lab already exist.
- Settings already include keyboard rebinding, volume controls, game speed, shake, reduced effects, high contrast, and stronger shape markers. These need completion and verification, not reinvention.

**Validation baseline.** `npm run build` passed with Vite 6.4.3 from the installed dependency tree. The emitted JavaScript was 140.26 kB / 45.19 kB gzip; CSS was 6.06 kB / 2.18 kB gzip. These are bundle sizes, not runtime performance results. `selfCheckPhysics()` returned an empty error list. There is no test script or broader automated regression suite in `package.json`.

**Additional source-level findings.** These are grounded in control flow and data, but were not all separately executed.

- **Time and repeatability:** `src/main.ts:8` clamps elapsed time to 0.033 seconds. `Simulation.update` uses variable frame time and speed-based substeps only for player movement; enemy collisions, projectiles, and several other systems update once per frame. `TUNE.fixedDt` and `maxFrame` are unused. Low frame rates lose elapsed game time. Attraction uses hard-coded 0.016/0.01 increments in `src/sim.ts:1295`. Particle generation consumes the same RNG as combat and future run decisions. A seed alone does not establish stable replay across frame rates or cosmetic changes.
- **Progression integrity:** permanent `save.embers` accumulate and display, but forging spends `run.embers`, which starts at zero; the permanent balance has no evident consumer. Evolutions assign non-common parts without calling `noteRarity`, potentially allowing the common-only achievement after a non-common evolution. Annealing's advertised free use is not tracked with an explicit once-per-run flag. Decide the intended rules before changing the economy.
- **Damage attribution and coverage:** `blastArea` sets `slamKill` for ability damage, including Air Burst, and the flag can survive a nonlethal hit. The collision-only boss achievement checks only whether ability damage is zero, permitting other non-collision damage. Run damage totals are fed primarily through `onHit`, missing ordinary enemy effect damage. Use a common damage record for statistics and achievements.
- **Boss build parity:** the boss is not an `FxEnemy`; direct effect damage, status, area, and chain actions commonly enumerate enemies or require an enemy context. Boss collision fires `onImpact` without an enemy; rivet hits omit that hook. Explosions and certain abilities explicitly support the boss. Several build identities therefore lose mechanics in the final encounter unless deliberately adapted. This requires balance testing and explicit resistance rules.
- **Lifecycle and hazards:** lava subtracts HP directly, bypassing shield and low-HP hooks used by `hurt`, including Second Wind. Updates continue through several systems after callbacks can end the room. Verify mutually exclusive death and clear outcomes and prevent post-death healing, rewards, or effects. The lab's god handling does not cover this direct lava path.
- **Equipment transactions:** rewards preserve health percentage on replacement, while shops and events directly change IDs and rely on later simulation clamping. Establish one health/energy policy for all equip and fusion paths. Account for consumed slots and lost synergies before purchase.
- **Input:** global key handling prevents Tab's browser focus behavior even in menus. Gamepad polling supports gameplay but has no complete menu focus/confirm/cancel system. `confirmPressed` is sampled but unused. Binding aliases remain hard-coded; there is no conflict detection or cancellation flow. Browser blur clears some held input but does not pause the run. Mouse thrust is observed globally, including interface clicks. Treat these as separate gameplay and UI contexts.
- **UI correctness:** the map shows columns of nodes but never renders `MapNode.next` connections. Reward and shop copy omit important information such as explicit numeric resource amounts in some cards, lost synergies, or the displaced component. `CardPreview` uses an illustrative movement model, despite copy claiming the same hop and bounce as the real ball. `refresh` caches markup with a key omitting permanent unlock/currency state, so forging in the codex can leave stale UI until another state change.
- **Accessibility and layout:** CSS focus outlines and live regions are good starting points. High contrast changes DOM styling but does not parameterize world rendering. Reduced effects still permit camera zoom, title motion, and several animations. The narrow-layout reward grid becomes one column, but full-page overflow is hidden and general panels have no scrolling constraint. The title has an inline two-column grid. Actual clipping, legibility, and contrast require browser inspection at small resolutions and zoom.
- **Performance and structure:** `Game.frame` recompiles the build each rendered frame, and `updateHud` rebuilds slot HTML every frame and sheet HTML while open. Dead enemies remain in arrays, and lab respawns keep adding entries. `sim.ts` combines movement, enemies, combat, boss, hazards, effects, and visuals in roughly 1,450 lines. Profile first; cache invariant data and isolate systems where that enables verification.
- **Persistence and resilience:** save loading merges parsed values without validating types, ranges, versions, or known IDs. Writes can throw without handling unavailable storage or quota errors. Active runs are not persisted. Save reset does not fully reapply settings/input/audio state. Introduce migrations and a recoverable failure path before relying on saves for a larger progression system.
- **Content contract drift:** `onDamaged` is declared but never dispatched; pickup attraction is a declared action target without a matching branch; ice is rendered differently but has no dedicated friction behavior. Wildfire's description says burn spreads, while its area action applies damage rather than neighboring burn. These are examples for a systematic content-to-behavior audit, not proof every declared extension point must become a shipped feature.

**Recommended direction.** Make the Foundry a polished, replayable demonstration of physically different builds. Use a minimum comparison set of balanced, heavy, light, rebound, fire, and magnetic builds. For each, establish a movement profile, a strong encounter, a difficult but feasible encounter, a viable boss strategy, and an understandable upgrade path. Do not equate a larger parts list with deeper decisions.

First restore trust in the run and simulation. Then improve feedback and control. Then strengthen the graph, comparisons, boss interactions, and progression. Only after those pass should additional encounter variants and an optional biome prototype expand the game. A useful first content experiment is one arena with a grounded run-up lane, an optional spring/rebound route, and enemies that reward different approaches; playtest it with both a heavy and a light core.

**Evidence still needed.** The implementation agent should capture the initial browser experience, test complete runs, measure room and run duration, inspect UI at 1280×720 and small windows, audition sound, test physical controllers, and profile representative high-effect combat. Human playtests are needed to judge fun, onboarding comprehension, fairness, and desire to try another build. Until then, targets in the companion prompt are proposed acceptance criteria, not measured facts.
